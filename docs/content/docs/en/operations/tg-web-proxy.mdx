FullBoard can install and manage
[tproxy-server](https://github.com/telegramdesktop/tproxy-server), the relay
that lets Telegram clients reach MTProxy over ordinary HTTPS or WebSocket
traffic. Open **Telegram WEB Proxy** in the sidebar (`/panel/tg-web-proxy`).

<Callout type="warn">
  Management needs a Linux host with systemd. On other hosts the page is
  read-only. The upstream installer supports Ubuntu/Debian x86_64 and takes over
  ports **80** and **443** with Caddy, so don't run it on a host where another
  web server or an Xray inbound already listens on those ports.
</Callout>

## How it fits together

| Unit              | Role                                                         |
| ----------------- | ------------------------------------------------------------ |
| `caddy`           | Public TLS on 443, forwards the proxy path to the relay      |
| `tproxy-server`   | The relay, listening on `127.0.0.1:8080` only                |
| `mtproxy`         | MTProxy backends the relay forwards each profile to          |
| `tproxy-firewall` | Firewall rules that keep the loopback ports closed to others |

The relay's admin listener (`127.0.0.1:8081` by default) exposes `/healthz`,
`/readyz` and `/metrics`. FullBoard reads it **server-side only** and shows the
result on the Overview tab; it is never published.

## Install

<Steps>

<Step>
### Prepare DNS

Point an A/AAAA record for the proxy hostname (for example `tg.example.com`) at
the server, and make sure ports 80 and 443 are free and reachable.
</Step>

<Step>
### Run the installer

On the **Overview** tab click **Install** and fill in the hostname, the ACME
email, the first profile's secret (generate one in the form), and optionally a
base path, a site to serve on the root (`--site-dir` or `--site-upstream`) and
the number of MTProxy workers.

FullBoard downloads the latest upstream source to `/usr/local/src/tproxy-server`
and runs `deploy/install.sh` as a transient systemd unit, so it survives a panel
restart. The secret is passed on stdin from a `0400` file that is deleted
afterwards; it never appears in a process list. The job log streams on the
Overview tab.
</Step>

<Step>
### Verify

When the job succeeds the units table should show every unit as active and the
admin probe as healthy and ready.
</Step>

</Steps>

**Update relay** re-downloads the upstream source and runs `deploy/update-relay.sh`.

### Adopting an existing install

If tproxy-server was installed by hand with the stock layout
(`/etc/tproxy-server/config.json`, `/etc/tproxy-server/profiles.json`,
`/usr/local/bin/tproxy-server`), FullBoard picks it up automatically: no
re-install is needed. Unknown keys in `config.json` are preserved on save.

## Profiles

Each profile is one entry in `profiles.json`:

- **Name**: unique, up to 64 characters.
- **Secret**: 32 hex characters (or `dd` + 32 hex). Secrets must be unique.
- **Backend**: a loopback `host:port` of an MTProxy instance, such as
  `127.0.0.1:8443`.
- **Carrier mode** (optional): `https`, `https-lanes`, `websocket` or
  `websocket-lanes`.
- **Limits** (optional): per-profile caps, which can't exceed the global limits.

<Callout type="info">
  The relay only forwards traffic. Each backend must be a running MTProxy that
  accepts the same secret, and the firewall must keep its port closed to the
  outside.
</Callout>

## Share links

Click **Share** on a profile to get the link, a `tg://` deep link and a QR code.
For a root deployment the link is
`https://t.me/webproxy?server=<hostname>&secret=<hex>`. With a base path the
server becomes `<hostname>/<base>` and the secret is encoded the way Telegram
expects for path deployments; FullBoard handles this for you.

## Client bindings

Bind a client to a profile so its **raw** subscription and the client **QR code**
menu carry a web-proxy link next to inbound links. Open the client's form, go to
the **Telegram WEB Proxy** tab and pick a profile, or review bindings under
**Profiles → Client bindings**. JSON and Clash subscriptions never include the
link.

- **Shared binding.** The client advertises the chosen profile's own secret.
  Everyone bound to that profile shares one secret; the profile's existing
  MTProxy backend must already accept that secret.
- **Dedicated secret.** FullBoard creates a profile named `fb:<email>`, cloned
  from the chosen one (carrier mode, limits) with a fresh random secret, and
  automatically provisions a loopback MTProto inbound (`fb-tgwp:<email>`) that
  accepts it — no hand-built inbound per secret. The profile is written to
  `profiles.json` by a background sync a few seconds after you save. The link
  appears once the sync finishes.
- Disabled clients and clients without a matching relay profile get no link.
- A profile that clients are bound to cannot be deleted or renamed, and `fb:`
  profiles are managed by FullBoard: edit them by unbinding the client.
- Deleting a client drops its binding and its `fb:` profile.

Shared bindings still require the chosen profile's backend to accept that
shared secret. Dedicated bindings own their backends: unbinding deletes the
`fb-tgwp:` inbound.

## Route backend via outbound

On a profile row, **Route via outbound** creates a loopback tunnel inbound
(dokodemo-style) that rewrites to the profile's current MTProxy backend, adds a
routing rule that sends that inbound's traffic to a chosen Xray outbound, then
rewrites the profile `backend` to `127.0.0.1:<tunnel-port>`. The remote MTProxy
must still accept the profile secret; private/geoip rules on the outbound can
block Telegram — verify after applying.

## Public site

The **Public site** tab manages a panel-owned landing page under
`/var/lib/fullboard/tproxy-site` (`index.html` editor, asset upload, sandbox
preview). Saving activates `public_dir` on that directory and clears
`public_upstream`.

## Config

The **Relay config** tab edits `config.json`: the hostname and base path, the listen
and admin addresses, the public upstream, global limits and timeouts. On a fresh
host with no profiles yet, the form also asks for the first profile, since the
relay refuses to start without one.

## Troubleshooting

**`read-only file system` when saving config or a profile.** The panel unit uses
`ProtectSystem=full`, which makes `/etc` read-only. FullBoard needs
`ReadWritePaths=-/etc/tproxy-server`. Stock installs from a current release
include it; if you see this error on an older unit, add a drop-in and restart:

```bash
sudo mkdir -p /etc/systemd/system/fullboard.service.d
sudo tee /etc/systemd/system/fullboard.service.d/20-tproxy.conf >/dev/null <<'EOF'
[Service]
ReadWritePaths=-/etc/tproxy-server
EOF
sudo systemctl daemon-reload
sudo systemctl restart fullboard
```

Then save the relay config / profile again in the panel.

## Safety guarantees

Every save (config or profile) goes through the same steps:

1. The input is validated. Listeners, the admin address, the public upstream and
   all backends must be numeric loopback addresses.
2. Candidate files are written next to the live ones, with `profiles.json` at
   mode `0400`.
3. `tproxy-server -config … -profiles-file … -check` validates the candidates.
   If it fails, the live files stay untouched and the error is shown.
4. The previous files are kept as `*.fullboard-prev`, and the candidates replace
   them.
5. If the relay was running, it is restarted. **Start** and **Restart** also run
   the check first.

The **Logs** tab shows the journal of any relay unit (10 to 1000 lines).
