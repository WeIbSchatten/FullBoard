<Callout type="warn">
  Take a backup before any migration, and keep the old panel available until
  you have checked the new one with a real client.
</Callout>

## From 3x-ui

We1ssBoard reads a 3x-ui database directly and carries over inbounds, clients,
their traffic and IP history, panel settings and the admin account. Every row is
checked against the source, and the import refuses to finish if anything was
lost. The 3x-ui database is opened read-only and never changed.

The migration script does the whole move on the same server and can undo it.
Requirements: root, systemd, and SQLite on both panels (the 3x-ui default).

<Steps>

<Step>
### Install We1ssBoard

Install it next to 3x-ui (see [Installation](/docs/guide/installation)). 3x-ui can
keep running: by default the installer picks a random panel port, so the two
panels do not clash. Do not give it 3x-ui's port.
</Step>

<Step>
### Run the migration script

```bash
bash <(curl -Ls https://raw.githubusercontent.com/WeIbSchatten/We1ssBoard/main/migrate-3xui.sh) migrate
```

The script:

1. runs a **test import** while 3x-ui is still serving clients; if it fails,
   nothing is stopped or changed. If it printed a `WARNING`, the script asks
   before going on;
2. stops both panels and backs up 3x-ui (database, `/usr/local/x-ui`, the
   service unit, the `x-ui` command and its env file) and the current
   We1ssBoard database to `/root/3x-ui-migration-<date>/`;
3. imports `x-ui.db`, disables `x-ui.service` and starts We1ssBoard;
4. if We1ssBoard does not stay up, puts 3x-ui back automatically and shows
   the last lines of the We1ssBoard log.

Add `--yes` to skip the confirmations, for example in automation.
</Step>

<Step>
### Log in

Open the panel at the **3x-ui** address and log in with your **3x-ui** username
and password: the port, web path and login came over with the settings. Client
links and subscription URLs stay the same, so clients do not need new configs.
</Step>

</Steps>

A `WARNING` in the import output means a value needs your attention, for
example a client whose inbounds disagreed on a limit, or a certificate file
that is missing on this server. The full output is saved as `import.log` in
the backup folder.

### Roll back to 3x-ui

```bash
bash <(curl -Ls https://raw.githubusercontent.com/WeIbSchatten/We1ssBoard/main/migrate-3xui.sh) rollback
```

This restores 3x-ui from the latest backup exactly as it was, including whether
its service was enabled and running, and checks the restored `x-ui.db` against
its checksum. The imported We1ssBoard database is kept in the backup folder. To
pick an older backup, pass its folder after `rollback`; `status` lists all
backups. Run the script without arguments for a menu with the same actions.

<Callout>
  IP limits only work with fail2ban. If fail2ban is not running, the import
  resets them to 0 exactly as a 3x-ui upgrade would, and says so.
</Callout>

### Manual import

Without the script (for example, without systemd), run the same import by hand.
Stop both panels so neither writes while you copy, move the fresh We1ssBoard
database aside (the import creates the database and will not overwrite one),
import, then switch services:

```bash
systemctl stop x-ui we1ssboard
mv /etc/we1ssboard/we1ssboard.db /etc/we1ssboard/we1ssboard.db.empty
/usr/local/we1ssboard/we1ssboard import-3xui -src /etc/x-ui/x-ui.db
systemctl disable --now x-ui
systemctl start we1ssboard
```

`-dst` writes the result to another file instead of the configured database,
which is handy for a dry run.

## From FullBoard

FullBoard was renamed to We1ssBoard in 1.7.0. Update as usual (from the panel or
with `we1ssboard update`): the updater moves everything to the new names and
leaves compatibility links behind, so nothing has to be done by hand.

| FullBoard | We1ssBoard |
| --- | --- |
| `/usr/local/fullboard` | `/usr/local/we1ssboard` |
| `/etc/fullboard/fullboard.db` | `/etc/we1ssboard/we1ssboard.db` |
| `fullboard.service` | `we1ssboard.service` |
| `fullboard` command | `we1ssboard` command |
| `fullboard-mtproxy-*` units | `we1ssboard-mtproxy-*` units |

If a server was updated while an older update was interrupted, it can end up
with files in both `/etc/fullboard` and `/etc/we1ssboard`. Updating to 1.7.1 or
later merges them; the panel log shows `readonly database` until that is done.

## To another server

Moving to a new server is a database move.

<Steps>

<Step>
### Back up the old server

Download a backup from **Overview → Backup & Restore** (or from the mobile app,
**Settings → Xray Updates → Back Up**), or copy `/etc/we1ssboard/we1ssboard.db`
and your certificates. See [Backup & restore](/docs/operations/backup-restore).
</Step>

<Step>
### Install and restore

Install the same or a newer We1ssBoard version on the new server, then restore
the backup from **Backup & Restore → Restore**. Turn on **Keep this machine's
settings** to keep the new server's ports, web path and certificates.
</Step>

<Step>
### Update addresses

Point your domain at the new server, or update the address in hosts and
subscription settings if clients connect by IP.
</Step>

</Steps>

## From SQLite to PostgreSQL

```bash
/usr/local/we1ssboard/we1ssboard migrate-db -dsn "postgres://user:pass@host:5432/we1ssboard?sslmode=disable"
```

Then set `XUI_DB_TYPE=postgres` and `XUI_DB_DSN` in the service environment and
restart the panel. See [Environment variables](/docs/reference/env-vars).

## Between We1ssBoard versions

Updating migrates the database by itself. Read the
[release notes](https://github.com/WeIbSchatten/We1ssBoard/releases) before a
major version and take a backup. A panel update installs the Xray version it
ships with, unless you pinned another one (see
[REALITY](/docs/config/reality#client-compatibility)).
