FullBoard умеет устанавливать и обслуживать
[tproxy-server](https://github.com/telegramdesktop/tproxy-server) — релей,
через который клиенты Telegram подключаются к MTProxy поверх обычного HTTPS или
WebSocket. Откройте **Telegram WEB Proxy** в боковом меню (`/panel/tg-web-proxy`).

<Callout type="warn">
  Для управления нужен Linux-хост с systemd; на остальных страница доступна
  только для чтения. Установщик поддерживает Ubuntu/Debian x86_64 и занимает
  порты **80** и **443** под Caddy, поэтому не запускайте его там, где эти порты
  уже заняты другим веб-сервером или inbound Xray.
</Callout>

## Как это устроено

| Юнит              | Назначение                                                    |
| ----------------- | ------------------------------------------------------------- |
| `caddy`           | Публичный TLS на 443, проксирует путь прокси на релей         |
| `tproxy-server`   | Релей, слушает только `127.0.0.1:8080`                        |
| `mtproxy`         | Бэкенды MTProxy, на которые релей направляет профили          |
| `tproxy-firewall` | Правила файрвола, закрывающие loopback-порты от внешнего мира |

Админ-листенер релея (по умолчанию `127.0.0.1:8081`) отдаёт `/healthz`,
`/readyz` и `/metrics`. FullBoard опрашивает его **только на стороне сервера** и
показывает результат на вкладке «Обзор»; наружу он не публикуется.

## Установка

<Steps>

<Step>
### Подготовьте DNS

Направьте A/AAAA-запись имени прокси (например, `tg.example.com`) на сервер и
убедитесь, что порты 80 и 443 свободны и доступны извне.
</Step>

<Step>
### Запустите установщик

На вкладке «Обзор» нажмите **Установить** и укажите имя хоста, email для ACME,
секрет первого профиля (его можно сгенерировать в форме) и, при необходимости,
базовый путь, сайт для корня (`--site-dir` или `--site-upstream`) и число
воркеров MTProxy.

FullBoard скачивает актуальные исходники в `/usr/local/src/tproxy-server` и
запускает `deploy/install.sh` во временном юните systemd, поэтому установка
переживает перезапуск панели. Секрет передаётся через stdin из файла с правами
`0400`, который затем удаляется; в списке процессов он не появляется. Лог задачи
выводится на вкладке «Обзор».
</Step>

<Step>
### Проверьте

После успешного завершения все юниты в таблице должны быть активны, а
админ-проверка — показывать healthy и ready.
</Step>

</Steps>

**Обновить релей** заново скачивает исходники и запускает `deploy/update-relay.sh`.

### Существующая установка

Если tproxy-server установлен вручную со стандартной раскладкой
(`/etc/tproxy-server/config.json`, `/etc/tproxy-server/profiles.json`,
`/usr/local/bin/tproxy-server`), FullBoard подхватит его автоматически,
переустанавливать не нужно. Неизвестные ключи в `config.json` при сохранении
сохраняются.

## Профили

Каждый профиль — запись в `profiles.json`:

- **Имя** — уникальное, до 64 символов.
- **Секрет** — 32 hex-символа (или `dd` + 32 hex), без повторов.
- **Бэкенд** — loopback `host:port` экземпляра MTProxy, например
  `127.0.0.1:8443`.
- **Режим транспорта** (необязательно) — `https`, `https-lanes`, `websocket`
  или `websocket-lanes`.
- **Лимиты** (необязательно) — не могут превышать глобальные.

<Callout type="info">
  Релей только пересылает трафик. Каждый бэкенд должен быть запущенным MTProxy с
  тем же секретом, а файрвол должен закрывать его порт снаружи.
</Callout>

## Ссылки для клиентов

Кнопка **Поделиться** у профиля показывает ссылку, deep link `tg://` и QR-код.
Для установки в корень ссылка выглядит как
`https://t.me/webproxy?server=<hostname>&secret=<hex>`. С базовым путём сервер
становится `<hostname>/<base>`, а секрет кодируется так, как ожидает Telegram;
FullBoard делает это сам.

## Привязки клиентов

Привяжите клиента к профилю — ссылка web-proxy появится в **«сырой»** подписке и
в меню **QR-код**. Откройте форму клиента, вкладку **Telegram WEB Proxy**, и
выберите профиль; все привязки видны в **Профили → Привязки клиентов**. В
подписках JSON и Clash этой ссылки никогда нет.

- **Общая привязка.** Клиент получает секрет самого выбранного профиля. У всех
  клиентов одного профиля секрет общий; backend профиля уже должен принимать
  этот секрет.
- **Отдельный секрет.** FullBoard создаёт профиль `fb:<email>`, скопированный с
  выбранного (режим carrier, лимиты), с новым случайным секретом и **сам**
  поднимает loopback MTProto-inbound (`fb-tgwp:<email>`), который этот секрет
  принимает — отдельный inbound вручную создавать не нужно. Профиль пишется в
  `profiles.json` фоновой синхронизацией через несколько секунд; ссылка
  появляется после неё.
- У отключённых клиентов и клиентов без профиля на релее ссылки нет.
- Профиль, к которому привязаны клиенты, нельзя удалить или переименовать, а
  профили `fb:` управляются FullBoard: чтобы изменить их, отвяжите клиента.
- При удалении клиента удаляются его привязка и профиль `fb:`.

Для общей привязки backend выбранного профиля по-прежнему должен принимать
общий секрет. Для отдельного секрета backend создаёт и удаляет панель сама
(inbound `fb-tgwp:` снимается при отвязке).

## Маршрутизация backend через outbound

На строке профиля **Route via outbound** создаёт loopback tunnel-inbound
(dokodemo), который переписывает трафик на текущий MTProxy backend профиля,
добавляет routing-правило на выбранный Xray outbound и меняет `backend` профиля
на `127.0.0.1:<порт-туннеля>`. Удалённый MTProxy по-прежнему должен принимать
секрет профиля; private/geoip-правила outbound могут резать Telegram —
проверьте после применения.

## Публичный сайт

Вкладка **Public site** управляет лендингом панели в
`/var/lib/fullboard/tproxy-site` (редактор `index.html`, загрузка ассетов,
preview в sandbox). Сохранение включает `public_dir` на этот каталог и очищает
`public_upstream`.

## Конфигурация

Вкладка «Конфигурация релея» редактирует `config.json`: имя хоста и базовый путь,
адреса листенера и админки, публичный upstream, глобальные лимиты и таймауты. На
новом хосте без профилей форма также запрашивает первый профиль — без него релей
не запустится.

## Устранение неполадок

**`read-only file system` при сохранении конфига или профиля.** Unit панели
использует `ProtectSystem=full`, из‑за чего `/etc` только для чтения. FullBoard
нужны `ReadWritePaths=-/etc/tproxy-server` и `CAP_CHOWN` (файлы `root:tproxy`).
В актуальном релизе это уже есть; на старом unit замените drop-in и
перезапустите:

```bash
sudo mkdir -p /etc/systemd/system/fullboard.service.d
sudo tee /etc/systemd/system/fullboard.service.d/20-tproxy.conf >/dev/null <<'EOF'
[Service]
ReadWritePaths=-/etc/tproxy-server
# Drop-in полностью заменяет CapabilityBoundingSet — нужен полный набор.
CapabilityBoundingSet=CAP_DAC_OVERRIDE CAP_NET_ADMIN CAP_NET_BIND_SERVICE CAP_NET_RAW CAP_CHOWN
EOF
sudo systemctl daemon-reload
sudo systemctl restart fullboard
```

После этого снова сохраните конфиг / профиль в панели.

**`permission denied` на `config.json` в логах `tproxy-server`.** Панель записала
файл как `root:root` (нет `CAP_CHOWN`). Исправьте владельца сейчас и примените
drop-in выше, чтобы следующее сохранение снова не ломало права:

```bash
sudo chown -R root:tproxy /etc/tproxy-server
sudo chmod 750 /etc/tproxy-server
sudo chmod 640 /etc/tproxy-server/config.json
sudo chmod 400 /etc/tproxy-server/profiles.json
sudo systemctl restart tproxy-server
```

## Гарантии безопасности

Любое сохранение (конфигурации или профиля) проходит одни и те же шаги:

1. Проверка ввода: листенеры, админ-адрес, публичный upstream и все бэкенды
   должны быть числовыми loopback-адресами.
2. Кандидаты записываются рядом с рабочими файлами, `profiles.json` — с правами
   `0400`.
3. `tproxy-server -config … -profiles-file … -check` проверяет кандидатов. При
   ошибке рабочие файлы не меняются, а ошибка показывается в интерфейсе.
4. Предыдущие файлы сохраняются как `*.fullboard-prev`, затем кандидаты их
   заменяют.
5. Если релей был запущен, он перезапускается. **Запуск** и **Перезапуск** тоже
   сначала выполняют проверку.
