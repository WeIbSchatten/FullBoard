Медленный прокси почти никогда не тормозит из-за одной настройки. Пройдите
страницу сверху вниз: каждый шаг убирает одно частое ограничение скорости или
задержки.

## 1. Сетевые настройки ядра (BBR)

Большинство дистрибутивов стартуют с алгоритмом `cubic`, очередью `fq_codel` и
маленькими буферами сокетов. На маршруте с RTT 50–200 мс это ограничивает один
TCP-поток намного ниже возможностей канала, а первая же потеря пакета снова
срезает скорость вдвое.

Начиная с **1.4.4** `install.sh` и `update.sh` записывают
`/etc/sysctl.d/99-fullboard-network.conf` и сразу его применяют:

| Параметр | Значение | Зачем |
| --- | --- | --- |
| `net.ipv4.tcp_congestion_control` | `bbr` | Темп по измеренной полосе, а не сброс скорости на каждую потерю |
| `net.core.default_qdisc` | `fq` | Очередь с пейсингом, под которую сделан BBR |
| `net.core.rmem_max` / `wmem_max` | 32 МиБ | Один поток может заполнить длинный широкий канал |
| `net.ipv4.tcp_rmem` / `tcp_wmem` | `4096 … 32 МиБ` | Потолок автонастройки для каждого сокета |
| `net.ipv4.tcp_mtu_probing` | `1` | Работа на маршрутах, которые молча теряют большие пакеты |
| `net.ipv4.tcp_slow_start_after_idle` | `0` | Скорость не сбрасывается после паузы (видео, сайты) |
| `net.ipv4.tcp_notsent_lowat` | `16384` | Короткие очереди отправки → ниже пинг под нагрузкой |
| `net.ipv4.tcp_fastopen` | `3` | На одно RTT меньше при переподключении |

Проверка на сервере:

```bash
sysctl net.ipv4.tcp_congestion_control net.core.default_qdisc
# net.ipv4.tcp_congestion_control = bbr
# net.core.default_qdisc = fq
```

Применить на старой установке, не дожидаясь обновления:

```bash
fullboard update        # заново выполнит настройку
# или только настройку вручную:
modprobe tcp_bbr
sysctl -p /etc/sysctl.d/99-fullboard-network.conf   # файл есть после 1.4.4
```

<Callout type="info">
  Чтобы оставить свои sysctl-настройки, задайте `XUI_NET_TUNING=false` в `/etc/default/fullboard` до
  установки или обновления. В контейнерах OpenVZ/LXC эти ключи часто менять нельзя — установщик тогда
  пропускает шаг и пишет об этом.
</Callout>

## 2. Выберите быстрый транспорт

Шифрование и упаковка стоят CPU и лишних RTT. От самого быстрого к самому
медленному на обычном VPS:

1. **VLESS + REALITY + `xtls-rprx-vision`** поверх TCP (Raw). Vision пропускает
   TLS-трафик без повторного шифрования — минимум CPU и задержки.
2. **XHTTP / gRPC / WebSocket + TLS** — нужны за CDN, но каждый байт шифруется
   дважды (TLS + участок до CDN), а CDN добавляет свою задержку.
3. **mKCP** и всё, что гоняет UDP внутри TCP, — только если TCP режут.

Не используйте **Mux** для замеров скорости и загрузок: он гонит много потоков
через одно TCP-соединение, и одна потеря тормозит их все.

## 3. Как читать нагрузку на CPU

Во время замера Xray расходует CPU примерно пропорционально скорости. На одном
vCPU 50–60 % при нескольких сотнях Мбит/с — норма, после теста нагрузка
возвращается к фону. CPU ограничивает скорость, только когда ядро упирается в
**100 %** — смотрите по ядрам:

```bash
top -1          # клавиша 1 показывает каждое ядро
```

Если одно ядро стоит на 100 %, переходите на REALITY + Vision (шаг 2) или на
тариф с большим числом или более быстрыми ядрами.

## 4. Чек-лист скорости

<Steps>
<Step>

**Замерьте сам сервер.** Если VPS напрямую не выдаёт нужную скорость, никакая настройка прокси не поможет.

```bash
curl -o /dev/null -w '%{speed_download}\n' https://speed.cloudflare.com/__down?bytes=200000000
```

</Step>
<Step>

**Замерьте пинг до сервера** со стороны клиента (`ping <server>`). Прокси добавляет задержку сверху, ниже этого значения не будет.

</Step>
<Step>

**Проверьте настройку** из раздела 1: должны быть `bbr` и `fq`.

</Step>
<Step>

**Проверьте без CDN** — подключитесь к IP сервера напрямую через REALITY. Если так быстро, а через CDN медленно, узкое место — CDN.

</Step>
<Step>

**Проверьте маршрутизацию.** Правило, отправляющее трафик через WARP или другой outbound, добавляет его ограничение скорости и задержку. Смотрите **Xray → Маршрутизация** и **Outbounds**.

</Step>
</Steps>
