Медленный прокси почти никогда не тормозит из-за одной настройки. Пройдите
страницу сверху вниз: каждый шаг убирает одно частое ограничение скорости или
задержки.

## 1. Управление перегрузкой (BBR) — сначала замер, потом решение

Большинство дистрибутивов стартуют с `cubic` и очередью `fq_codel`. **BBR + fq**
часто помогает на длинных чистых маршрутах, но на каналах с полисерами и шейпингом
может давать больше потерь, ниже скорость и выше пинг, чем `cubic`. Установка и
обновление включают BBR вместе с QUIC-буферами (см. ниже); `XUI_QUIC_TUNING=false` оставляет `cubic`.

<Callout type="warn">
  1.4.4 и 1.4.5 автоматически включали расширенный профиль (BBR, буферы 32 МиБ, `tcp_notsent_lowat`,
  принудительный `fq` на интерфейсах). На части серверов скорость и пинг от этого стали хуже.
  Обновление до 1.4.6 удаляет `/etc/sysctl.d/99-fullboard-network.conf` и возвращает настройки ядра
  по умолчанию.
</Callout>

Сравните оба варианта на своём маршруте — после каждого шага повторите один и тот же замер:

```bash
# A: по умолчанию
sysctl -w net.ipv4.tcp_congestion_control=cubic net.core.default_qdisc=fq_codel
# B: BBR
modprobe tcp_bbr && sysctl -w net.ipv4.tcp_congestion_control=bbr net.core.default_qdisc=fq
```

`sysctl -w` действует до перезагрузки. Победителя закрепите пунктом **BBR** в меню
`we1ssboard` или задайте `XUI_NET_TUNING=true` в `/etc/default/we1ssboard` и выполните
`we1ssboard update` (будут записаны только эти два ключа).

Признак полисера на маршруте — много повторных передач во время загрузки
(`nstat -az TcpRetransSegs` быстро растёт, в `ss -tin` видно `retrans:`).

### UDP-буферы для QUIC (Hysteria, TUIC)

Xray открывает сокеты Hysteria и TUIC, не запрашивая размер буфера, и они получают
`net.core.rmem_default` (208 КиБ). Всплески трафика его переполняют, ядро отбрасывает
пакеты, а `nstat -az UdpRcvbufErrors` растёт (в играх это лаги). Поэтому установка и
обновление записывают `/etc/sysctl.d/99-quic.conf`: `net.core.{r,w}mem_default` 4 МиБ,
`net.core.{r,w}mem_max` 16 МиБ (если на сервере уже больше, значение сохраняется) и
`tcp_congestion_control = bbr`, если ядро поддерживает BBR, а затем перезапускают панель,
чтобы Xray пересоздал сокеты. Проверка: `ss -uamp` (`rb4194304` на порту Hysteria).
Чтобы отказаться, задайте `XUI_QUIC_TUNING=false` в `/etc/default/we1ssboard` и выполните
`we1ssboard update` (файл удаляется, стандартные значения вернутся после перезагрузки).
Если выключить BBR только в меню, следующее обновление включит его снова. В Docker эти
ключи задаются на хосте.

## 2. Выберите быстрый транспорт

Шифрование и упаковка стоят CPU и лишних RTT. От самого быстрого к самому
медленному на обычном VPS:

1. **VLESS + REALITY + `xtls-rprx-vision`** поверх TCP (Raw). Vision пропускает
   TLS-трафик без повторного шифрования — минимум CPU и задержки.
2. **XHTTP / gRPC / WebSocket + TLS** — нужны за CDN, но каждый байт шифруется
   дважды (TLS + участок до CDN), а CDN добавляет свою задержку.
3. **mKCP** и всё, что гоняет UDP внутри TCP, — только если TCP режут.

Не используйте **Mux** для замеров скорости и загрузок: он гонит много потоков
через одно TCP-соединение, и одна потеря тормозит их все.

## 3. Как читать нагрузку на CPU

Во время замера Xray расходует CPU примерно пропорционально скорости. На одном
vCPU 50–60 % при нескольких сотнях Мбит/с — норма, после теста нагрузка
возвращается к фону. CPU ограничивает скорость, только когда ядро упирается в
**100 %** — смотрите по ядрам:

```bash
top -1          # клавиша 1 показывает каждое ядро
```

Если одно ядро стоит на 100 %, переходите на REALITY + Vision (шаг 2) или на
тариф с большим числом или более быстрыми ядрами.

## 4. Чек-лист скорости

<Steps>
<Step>

**Замерьте сам сервер.** Если VPS напрямую не выдаёт нужную скорость, никакая настройка прокси не поможет.

```bash
curl -o /dev/null -w '%{speed_download}\n' https://speed.cloudflare.com/__down?bytes=200000000
```

</Step>
<Step>

**Замерьте пинг до сервера** со стороны клиента (`ping <server>`). Прокси добавляет задержку сверху, ниже этого значения не будет.

</Step>
<Step>

**Сравните BBR и cubic** (раздел 1) на своём маршруте.

</Step>
<Step>

**Проверьте без CDN** — подключитесь к IP сервера напрямую через REALITY. Если так быстро, а через CDN медленно, узкое место — CDN.

</Step>
<Step>

**Проверьте маршрутизацию.** Правило, отправляющее трафик через WARP или другой outbound, добавляет его ограничение скорости и задержку. Смотрите **Xray → Маршрутизация** и **Outbounds**.

</Step>
</Steps>
